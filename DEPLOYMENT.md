# Public Website Deployment

Cabin Bring Board can run as a normal public website URL. Family members open the URL on iPhone Safari and can add it to the Home Screen.

## Recommended Host

Use a managed Node host with persistent storage. The current recommended target is Render because this app already runs as one small Node web service and stores shared trip state in one JSON file.

Static-only hosting is not enough for the shared family board. A static site can show the interface, but it cannot keep everyone synced unless it also has a backend or database. This app needs:

- HTTPS public URL
- One running Node process for `/api/state`, `/api/action`, and `/api/events`
- Persistent storage for `data/cabin-state.json`
- shared-password protection and adult-name login
- blocked HTTP/HTTPS write failures, so one phone cannot silently diverge from the shared board

## Render Setup

This repo includes `render.yaml` for a Render Blueprint.

The blueprint creates:

- a Node web service
- a persistent disk mounted at `/var/data`
- `DATA_DIR=/var/data`, so live state survives deploys/restarts
- `SESSION_SECRET` generated by Render
- deterministic install with `npm ci`
- manual `APP_PASSCODE`, `APP_ADMIN_PASSCODE`, and `PUBLIC_ORIGIN` environment variables
- health check at `/api/health`
- `NODE_ENV=production`, which makes missing `APP_PASSCODE` fail closed

## Required Environment Variables

Set these in Render before sharing the URL:

- `APP_PASSCODE`: set this to `1333` for the simple family launch
- `APP_ADMIN_PASSCODE`: separate admin passcode for reset, or same value if you do not want a separate one
- `PUBLIC_ORIGIN`: recommended once the final URL is known, for example `https://your-site.onrender.com`

Do not leave `APP_PASSCODE` blank on a public URL. In production, the app blocks API access when `APP_PASSCODE` is blank.

## Login / Profile Behavior

Current login flow:

- choose one adult name
- enter the shared password `1333`

Allowed login names are Shell, Nick, Marissa, Bear, Jessica, Andy, and Natalie. Kids do not log in. For the simplest setup, run the app with `APP_PASSCODE=1333` so the one visible password field also satisfies API access.

## iPhone Install Flow

After deployment:

1. Open the public HTTPS URL on iPhone Safari.
2. Tap the Share button.
3. Tap Add to Home Screen.
4. Keep the default app name or rename it.
5. Open from the Home Screen icon.

After login, the app shows this install guidance inside the dashboard unless it is already running from the Home Screen or the user dismissed the prompt. Chromium-style browsers that fire `beforeinstallprompt` use the native install prompt.

The app uses:

- `manifest.webmanifest`
- `assets/apple-touch-icon.png`
- `assets/icon-192.png`
- `assets/icon-512.png`
- `service-worker.js`

The service worker caches app shell assets and shows an update-ready control when a new shell is waiting.

## Deployment Checks

After the URL is live:

```bash
curl https://YOUR-URL/api/health
curl -I https://YOUR-URL/
```

Then verify in the browser:

- app loads over HTTPS
- profile can be created by tapping an attendee name, entering invite code, email, and optional password
- selected attendee pre-fills the right first name and family
- after sign-in, family pickers show the profile family as locked unless the user signs out
- existing passwordless profiles cannot be moved to another family from a fresh session
- passkey setup/sign-in requires Face ID, Touch ID, or device passcode on supported Apple devices
- sync status becomes live after profile login
- the in-app install panel appears after login when not already installed
- shared Shell/cabin checklists persist after refresh
- a meal can be claimed and then unclaimed by the signed-in family
- selected family can claim and unclaim a supply
- a custom meal idea or supply item can be added, edited, and deleted
- another signed-in family cannot edit or delete custom items it did not add or own
- each signed-in family can add and remove one vote per activity
- a direct API request with an unknown activity id is rejected
- another browser/device sees the update
- refreshing preserves state
- Home Screen install works on iPhone
- simulated network/server action failure does not locally change claims, votes, checklists, or added items as if they were shared

## Data Safety

The persistent live state is written to:

```text
/var/data/cabin-state.json
```

Profile/session data is written to:

```text
/var/data/users.json
```

The bundled starter state remains:

```text
data/seed-state.json
```

If the persistent disk is removed, the app will fall back to the bundled seed state.
